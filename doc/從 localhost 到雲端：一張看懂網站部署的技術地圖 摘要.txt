# 從 localhost 到雲端：一張看懂網站部署的技術地圖

本集以丁丁泡沫紅茶從一人小店走向可複製企業的故事，對照網站從本機開發走向正式上線的不同部署方式。內容依序介紹本機試營運、VM／VPS 所代表的 IaaS、Docker 與 CaaS、免自行打包的 PaaS，以及按事件執行的 FaaS，並說明前端、後端與資料庫在部署時各自要考量的問題。影片最後整理出一套部署決策地圖，協助初學者依照是否需要編譯、是否使用 Docker、服務是否長時間運作等條件，選擇 EC2、Vercel、Render、Cloud Run、Lambda 等工具。

## [00:00 - 00:26] 這一集要解決的問題：網站完成後該放在哪裡

上一集談到丁丁泡沫紅茶從一人小店成長為大型企業，核心問題是系統如何承受越來越多的客人；本集則把焦點轉向另一個階段：如何讓客人順利拿到飲料，對應到網站技術就是如何部署服務。影片不打算一次教完所有部署工具，而是先建立一張概念地圖，讓學習者未來聽到 EC2、Vercel、Render 或 Lambda 時，能理解它們在部署架構中的大致位置。

## [00:26 - 00:45] 丁丁泡沫紅茶的起點：從家裡試做飲料開始

丁丁在接受人物專訪時提到，自己在開店以前就很喜歡在家裡製作飲料，親朋好友試喝後也都認為味道很好，這才逐漸產生開店的念頭。主持人以幽默方式指出，總不能永遠邀請大家到客廳喝茶，因此丁丁才開始思考如何把個人興趣轉化為真正的生意。這段故事為後續網站部署的比喻埋下基礎：個人電腦上的作品，就像家裡自己做的飲料，還沒有真正對外提供服務。

## [00:45 - 01:08] localhost 為什麼只能自己連得上

網站剛寫好時，通常只能在開發者自己的電腦上執行。使用者可以在瀏覽器輸入 `localhost:3000`，看到畫面、操作按鈕，甚至儲存資料，但其他人卻無法連入，因為 `localhost` 指的是「目前這台自己的電腦」。因此，網站能在本機運作並不代表已經完成部署；真正的部署，是讓原本只有自己能執行的程式，變成外部使用者也能實際使用的服務。

## [01:08 - 01:23] 部署一定包含的三件事

影片將部署拆成三個基本動作。第一，是把程式放到外部可以連線的位置；第二，是把服務真正啟動起來；第三，是提供使用者可以進入的網址、APP 或其他入口。換句話說，部署不只是把程式碼上傳到某個地方，而是要讓服務能持續運作，並透過可使用的入口被外部使用者存取。

## [01:23 - 02:38] 本機試營運：用 ngrok 或 Cloudflare Tunnel 做短期驗證

丁丁在正式租店面前，先在家門口擺攤試營運，以低成本確認街坊鄰居是否真的喜歡這項產品。網站也可以用自己的電腦提供外部連線，這很適合 Demo、測試與短期市場驗證；Cloudflare Tunnel 和 ngrok 都能建立臨時通道，讓外部使用者連到本機上的服務。

然而，本機部署不適合長期正式營運，因為電腦可能關機、斷網、進入睡眠、切換 Wi-Fi，任何一種狀況都可能讓服務消失。除非能確保家中電腦長時間穩定供電且不中斷網路，否則這種方式比較像丁丁的門口試營運，而不是正式店面。當測試確認有需求後，就需要把服務搬到更穩定的環境。

## [02:38 - 03:33] 租一台雲端電腦：IaaS 的自由與責任

丁丁在確認市場接受度後，租下一間空店面，從空間配置、櫃台、冰箱到出餐口都能自行規劃。對應到網站部署，就是在雲端租用一台較穩定、不容易斷電斷線的電腦，也就是虛擬機器 VM 或虛擬私人伺服器 VPS。工程師可以在其中安裝 Node.js、Python、資料庫與其他系統套件，因而擁有最大的環境自由度，特別適合早期系統尚未穩定、需要快速修改與測試的情境。

這種模式的代價是所有維運責任都要自行承擔，包括安裝套件、啟動服務、查看 Log、製作備份、設定 HTTPS，以及服務掛掉後重新啟動。這就是 IaaS，也就是 Infrastructure as a Service，中文稱為基礎設施即服務：平台只提供 CPU、記憶體、硬碟、網路與 IP 等底層資源，作業系統、套件、監控與備份則由使用者負責。IaaS 的核心是自由度最大，但責任也最大。

## [03:33 - 05:11] EC2、Lightsail、Linode 與 Vultr：如何挑選雲端主機

常見的 IaaS 供應商包括 AWS 的 EC2 與 Lightsail、GCP 的 Google Compute Engine，以及 Azure VM。這些大型平台都有完整的雲端生態系和周邊服務，適合預期未來會發展成大型系統，或需要完整資安規範與整合能力的專案。若希望設定更簡單、操作不要過度複雜，也可以選擇 DigitalOcean Droplet、Linode 或 Vultr 等服務。

這些平台本質上都是租一台雲端電腦，但在規格選項、價格呈現與計費規則上有所不同。有些平台提供較少但容易理解的選項，有些則能細緻調整各項資源，同時也帶來較複雜的收費方式。影片以房東作比喻：有些會依照人流增加費用，有些則採固定租金。第一次部署時，選擇簡單、容易上手的服務即可；若一開始就確定會做大型系統，則可考慮 AWS、GCP 或 Azure。無論選哪一家，都應每天查看使用量與帳單，尤其 AWS 的服務組合很多，若沒有留意，帳單可能遠超預期。

## [05:11 - 06:28] 從單店複製到多店：Docker 解決環境一致性

丁丁事業的轉捩點，是專業經理人建議他不要只思考一間一間開店，而要把開店流程整理成可複製的系統。即使飲料製作已經完成 SOP，每間分店仍要重新找店面、裝潢、安裝冷氣、拉水電、裝網路，並確保設備規格一致，因此丁丁後來找統包廠商，將完整開店規格交給對方處理，等硬體與設備完成後，員工就能直接進場營業。

網站中的 Docker 就扮演類似角色。它會把程式碼所需的環境、套件版本與啟動方式，打包成標準化格式，降低「在我的電腦可以跑，搬到雲端卻壞掉」的問題。不過 Docker 只負責把服務包裝好，不會決定服務要在哪台機器上運作，也不會自動處理外部流量，因此還需要其他平台協助執行與管理容器。

## [06:28 - 07:39] CaaS：把 Docker 容器交給平台統包處理

CaaS 是 Container as a Service，也就是容器即服務，可以理解為網站部署世界中的統包廠商。開發者只要提供打包完成的 Docker image，平台便能協助找地方執行服務、啟動容器，並在服務掛掉時重新啟動；當新版本推出時，平台也能負責更新部署，流量增加時則可配置更多資源。

此外，CaaS 通常還會協助連接網址與 HTTPS，並整合 Log、監控與告警等觀測能力。Google Cloud Run、AWS App Runner 與 Azure Container Apps 都提供類似能力，讓開發者不必每次登入伺服器，手動安裝環境與啟動服務。更進階的 AWS ECS，則是用來管理一群容器，包括容器要運行在哪些機器、需要執行幾份、故障時是否重啟，以及流量如何分配，因此較適合服務數量增加、架構變得正式的系統。

## [07:39 - 08:08] PaaS：不用先打包 Docker 也能部署

PaaS 是 Platform as a Service，也就是平台即服務。與 CaaS 必須先準備 Docker image 不同，PaaS 只需要交付原始碼，平台會自行判斷專案類型、安裝所需套件、編譯程式並啟動服務。這種方式比 CaaS 再多處理一層基礎工作，因此使用門檻通常更低，適合希望快速把應用程式上線的開發者。

代價是對執行環境細節的控制力較少，使用者不能像租 VM 一樣任意調整所有設定。Heroku、Render 與 Railway 都屬於這類服務，適合不想自行管理太多伺服器細節，但仍希望部署一般應用程式的情境。

## [08:08 - 08:40] 重要提醒：不要把正式資料存放在 CaaS 或 PaaS 本機

CaaS 與 PaaS 很適合執行程式，卻不適合直接存放重要資料。平台可能因為更新、故障或流量調整而重啟服務、搬移服務，甚至同時開出多份服務；因此存放在服務本機的資料，不能被視為永久可靠的儲存空間。

會員資料、訂單資料與圖片檔案，應該另外放在資料庫或平台提供的儲存服務中。程式能順利跑起來，只代表運算服務已經啟動，不代表該機器適合承擔資料保存責任；運算環境與持久化資料應該分開設計。

## [08:40 - 09:10] 前端部署：靜態檔案與需要編譯的專案

部署時還可以進一步區分前端與後端。前端主要處理畫面、圖片、CSS 與 JavaScript，常見方式分成兩種。第一種是靜態檔案部署，網站已經產生可直接使用的 HTML、CSS 與 JavaScript，不需要再次編譯，此時可以使用 GitHub Pages、Firebase Hosting，或 AWS S3 搭配 CloudFront。

第二種是仍保留原始碼、必須先編譯才能執行的前端專案，則可使用 Vercel、Netlify 或 Cloudflare Pages。這些工具除了託管檔案，也通常整合編譯、預覽環境與環境變數管理，因而更適合現代前端框架的部署流程。

## [09:10 - 10:14] 後端與資料庫：不要只部署 API

後端部署處理的是 API、資料庫連線、登入、付款、訂單與庫存等商業邏輯。Heroku、Render、Railway、Cloud Run、App Runner，以及更進階的 ECS，都可以用來部署後端服務，但後端通常不只是單一 API，背後還需要資料庫保存會員、訂單、付款紀錄與商品資料。

小型專案可以先使用平台附帶的 PostgreSQL；當資料開始變得重要，則通常會採用託管資料庫，例如 AWS RDS。RDS 的本質仍然是 PostgreSQL 或 MySQL，只是把備份、升級與部分維護工作交給平台處理。影片不建議新手一開始就在 VM 裡自行安裝資料庫，因為安全性、備份、升級與故障處理都必須自己負責，所以後端部署時，資料庫放在哪裡必須同步規劃。

## [10:14 - 11:39] FaaS：像禮盒代工一樣按需求執行函式

丁丁不會讓每間分店都購買製作節日禮盒所需的特殊設備，分店只負責接單，收到訂單後再交給外包代工廠；代工廠做一盒才收一盒的費用，沒有訂單時也不必承擔設備閒置成本。網站中的 FaaS，也就是 Function as a Service，函式即服務，採用相似概念：開發者只撰寫一段獨立的程式邏輯，平台在請求或事件發生時才執行它。

FaaS 通常依實際使用量計費，執行次數越多、消耗資源越多，費用就越高。AWS Lambda、Cloudflare Workers、Vercel Functions 與 Netlify Functions 都是常見選項。它特別適合圖片壓縮、影片轉檔、產生 PDF、付款後寄送通知，以及每天凌晨產生報表等「事件觸發、執行完成後就結束」的任務。把這些工作拆出主後端，可以避免主服務為了少數任務長期使用更高規格的機器。

## [11:39 - 12:05] 冷啟動：FaaS 的延遲與使用限制

FaaS 並不適合所有後端服務。若任務執行時間很長，或需要持續維持連線，就不一定適合使用函式即服務。此外，當一段時間沒有請求時，平台可能會回收原本的執行環境；下一次任務到來時，平台必須重新建立環境並載入程式，這段等待就稱為冷啟動。

因此，若每次請求都要求非常即時、延遲極低，FaaS 可能不是理想選擇。以丁丁的代工廠為例，收到禮盒訂單後必須重新設定產線、替換材料，這段重新準備的時間就類似函式服務的冷啟動成本。

## [12:05 - 12:23] IaaS、CaaS、PaaS 與 FaaS 的一句話比較

影片用飲料店的分工重新整理四種服務。IaaS 像是租下一間店面，所有設備與營運環節都由自己處理；CaaS 像是把完整的飲料製作 SOP 交給統包商，請對方依規格執行；PaaS 則只提供飲料配方，其他環境與執行細節由平台決定；FaaS 則像有訂單時才找代工廠製作，沒有需求時不必持續維持完整產線。

## [12:23 - 13:22] 部署決策地圖：用幾個問題選擇合適工具

部署前首先要確認要處理的是前端還是後端。若是前端，接著判斷是否已經產生可直接使用的靜態檔案：若是，可以考慮 GitHub Pages，或使用 AWS S3 加 CloudFront；若專案仍需從原始碼編譯，則可考慮 Vercel 或 Cloudflare Pages。

若是後端，先判斷服務是否需要長時間執行、持續保持連線，或非常在意冷啟動延遲。若沒有這些需求，而且工作屬於事件觸發、完成後即結束，就可以考慮 AWS Lambda、Cloudflare Workers 或 Vercel Functions。若服務需要長時間運作，再確認是否使用 Docker：使用 Docker 時可考慮 Cloud Run、AWS App Runner，或在規模更大時使用 ECS；不使用 Docker 時，則可考慮 Heroku、Railway 或 Render。

如果不想把部署方式拆得太細，直接租用一台 VM，把所有服務集中在同一台機器上也可以完成部署。這種方法不一定是錯誤選擇，只是需要自行承擔更多環境管理與維運責任，適合希望先用單一主機快速完成整體架構的人。
